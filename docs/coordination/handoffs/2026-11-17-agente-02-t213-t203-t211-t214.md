## O que foi feito

### T-213 — partição `proposals` do PNCP (ADR-023)
- `source.sync` aceita `feed: 'proposals'`. O conector consulta `/consulta/v1/contratacoes/proposta?dataFinal=…&codigoModalidadeContratacao=…&pagina=…&tamanhoPagina=50`, uma modalidade por vez, em sequência. `dataFinal` = hoje + `PNCP_PROPOSALS_HORIZON_DAYS` (padrão 180).
- **Cursor por feed** em `Source.lastCursor`: `{ v: 2, feeds: { updates?, proposals? } }`. O formato antigo (cursor `updates` solto) continua aceito. A gravação trava a linha (`select … for update`) e o conector mescla (`storeCursor`), então os dois feeds não se sobrescrevem. Varredura concluída vira `done` e a próxima recomeça do início com `dataFinal` renovado.
- **Orçamento de 10 min por execução** (`SOURCE_SYNC_MAX_MS`, padrão 600000): ao esgotar, o sync para no cursor (`stoppedBy: 'time_budget'`) e o handler **reenfileira o mesmo payload** com `startAfter` de 30 s (`singletonKey` evita duplicata). `JOB_DEFAULTS` não foi alterado. A retomada vale só para `feed=proposals` + `mode=incremental` (`time_budget`, `max_pages`, `enrich_budget`).
- **429 nunca é retentado**: o cliente (`src/lib/pncp/client.ts`) lança `PncpRateLimited` na 1ª resposta 429, sem retentativa; o conector abre o cooldown (15 min, `PNCP_429_COOLDOWN_MS`) e lança `SourceRateLimited`; o sync termina `partial` com `stoppedBy: 'rate_limited'`, **sem lançar** (não consome `retryLimit` do pg-boss), cursor mantido na página; o handler reenfileira o mesmo payload só **depois do cooldown**. Com o disjuntor aberto, nenhuma chamada sai.
- Agendamento: `SOURCE_PROPOSALS_CRON` (padrão `23 */6 * * *`, vazio desliga). Os dois crons existentes não mudaram. Lock advisory por fonte **e feed**.
- "Nada é descartado": todo registro da listagem de propostas é gravado (já era o comportamento do sync); enriquecimento só para quem casa com perfil, com o orçamento de sempre.

### T-203 — `document.fetch`
- `src/server/sources/documents/download.ts` + `fetch.ts`; handler registrado em `buildRegistry`.
- **Sem SSRF**: só HTTPS de `pncp.gov.br`/`*.pncp.gov.br` (IP literal nunca passa); o nome é resolvido e **todos** os endereços precisam ser públicos (loopback, privado, link-local/metadados 169.254.169.254, CGNAT, multicast, IPv6 ULA/link-local e IPv4 mapeado são recusados); redirecionamento manual, máx. 3 saltos, cada `Location` revalidado; sem seguir para fora.
- **Limites**: tamanho (`DOCUMENT_MAX_BYTES`, 50 MB) conferido no cabeçalho **e** na leitura em fluxo (não confia no `Content-Length`); timeout (`DOCUMENT_FETCH_TIMEOUT_MS`, 60 s); espaçamento `PNCP_MIN_INTERVAL_MS` respeitado.
- **Tipo pelo conteúdo** (bytes), não pelo `Content-Type` da origem: PDF, OOXML/ODF (por ZIP + extensão), OLE (doc/xls), ZIP/RAR/7z (guardados, não extraíveis) e texto. HTML de erro, executáveis e binário desconhecido são rejeitados.
- Guarda em `public/<opportunityId>/<sha256>.<ext>`; atualiza **só** `storageKey`, `sha256`, `sizeBytes`, `mimeType`, `fetchedAt` (campos do agente 02; `textStatus` etc. intocados). Enfileira `document.extract` na **mesma transação** (formatos extraíveis).
- Rejeição definitiva (URL, endereço, tamanho, tipo, 404) **não lança**: grava `AuditEvent` `document.fetch_rejected` (só host e motivo, nunca a URL completa) e termina. Falha passageira (rede/5xx/DNS) lança e o pg-boss retenta. 429 reenfileira o mesmo job após o cooldown.
- Só documento **público** de origem `source` (certidões/uploads privados seguem T-212, não passam aqui).
- Dois documentos da mesma oportunidade com bytes idênticos: o 2º é registrado (`sha256`, `fetchedAt`) com `storageKey` nulo, porque a chave é única (retorna `duplicateOf`). Limitação conhecida e documentada.
- Resíduo registrado no código: o `fetch` resolve o DNS de novo (janela de DNS rebinding); a allowlist do domínio do PNCP (que a origem não controla) é a defesa principal.

### T-211 — `source.enrich` (ADR-021)
- `source.sync` enfileira `source.enrich { sourceRecordId }` (com espera de 5 min, `SOURCE_ENRICH_RETRY_DELAY_MS`) para o registro que casou com perfil e ficou só com a listagem por falha ou pausa do enriquecimento (inclusive o que não foi regravado por estar inalterado).
- `src/server/sources/enrich-record.ts`: grava **nova versão** enriquecida (a antiga nunca é alterada) e enfileira `source.normalize` na mesma transação; idempotente (já enriquecido → nada; mesmo conteúdo → mesmo `payloadHash`); só enriquece o que ainda casa com perfil ativo; 429 reenfileira após o cooldown; esgotadas as 3 tentativas, o handler registra `AuditEvent` `source.enrich_failed` e a oportunidade continua só com a listagem.

### T-214 — resultados homologados por item
- PNCP: `/itens/{n}/resultados` só para compra com resultado e itens com `temResultado`, até `PNCP_MAX_ITENS_RESULTADOS` (20) por compra, sequencial (≥ 1 s entre chamadas). 404 de um item = sem resultado; 429 para tudo; outra falha propaga e o `source.enrich` retenta.
- `OpportunityItem.awarded*`: vencedor = maior quantidade homologada (empate: menor preço), ignora cancelado/sem preço. **CPF de pessoa física nunca é gravado** (`awardedSupplierCnpj` só com 14 dígitos).
- `normalize-record` só escreve/limpa `awarded*` quando o payload **consultou** os resultados; uma listagem sem eles nunca apaga o vencedor já gravado. `isEnriched` passa a exigir `resultados` em compra homologada, então registros homologados já gravados são reenriquecidos na próxima leitura. `/prices` não mudou (já lê `awarded_unit_value`).
